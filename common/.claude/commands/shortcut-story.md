# Shortcut Story

Аналізує сторі в Shortcut, оцінює час виконання і — якщо потрібно — розбиває її на сабтаски (дочірні сторі) через Shortcut MCP. **Нічого не створюється у Shortcut без явного підтвердження.**

**Використання:** `/shortcut-story [Story ID або URL]`

---

## Крок 0 — Визначення сторі

З `$ARGUMENTS` витягнути ідентифікатор сторі:
- Якщо передано число (напр. `40737`) — це Story ID.
- Якщо передано URL (напр. `https://app.shortcut.com/.../story/40737/...`) — витягнути числовий ID зі шляху.

Якщо аргумент не передано:

> "Вкажи ID або URL сторі в Shortcut."

Дочекатися відповіді перед продовженням.

---

## Крок 1 — Перевірка доступу до Shortcut MCP

Переконатися, що доступні інструменти Shortcut MCP (`mcp__shortcut__*`). Якщо їх немає:

> "Shortcut MCP-сервер недоступний. Перевір що:
> 1. У `automation/.env` заданий `SHORTCUT_API_TOKEN`
> 2. Запущено setup-скрипт для цього проєкту (щоб згенерувати `.mcp.json`)
> 3. Claude Code перезапущено, а `/mcp` показує `shortcut` як підключений"

І зупинитись.

---

## Крок 2 — Збір інформації

Через інструменти Shortcut MCP отримати по сторі:
- **Title** і **description**
- **Існуючі сабтаски** (дочірні сторі / sub-tasks) — щоб не дублювати їх при розбивці
- **Коментарі**
- **External Links** і **Story Relationships**

Опрацювати вкладення та матеріали:
- **Зображення** — описати контекстно (що на них і як стосується задачі).
- **PDF / Word** — прочитати текст.
- **Посилання / External Links** — відкрити (WebFetch) і врахувати зміст.
- **Відео** (Loom, Fathom тощо) — спочатку шукати транскрипт у description/коментарях; якщо немає — спробувати отримати через URL.

**Якщо будь-яке вкладення, посилання чи відео не вдається прочитати** — не пропускати мовчки, а повідомити користувача й попросити надати контент у зручному форматі:

> "Не вдалося прочитати \<що саме\> (\<причина\>). Можеш надати зміст текстом, скріншотом або коротким описом?"

Дочекатися, поки матимеш достатньо контексту для оцінки.

---

## Крок 3 — Аналіз контексту проєкту

Перш ніж оцінювати — розібратися в коді, якого стосується задача. Це робить естімейт і FE/BE-поділ значно точнішими.

1. **Знайти project map воркспейсу.** Знайти CLAUDE.md рівня воркспейсу — той, що містить «Project map» / опис відповідальності репозиторіїв. Перевірити поточну директорію та її батьківську (`./CLAUDE.md`, `../CLAUDE.md`). Прочитати його, щоб зрозуміти які репозиторії існують і який відповідає за фронтенд, а який — за бекенд.

2. **Визначити релевантний FE-проєкт.** Спробувати визначити автоматично з поточної директорії (якщо CWD — один із проєктів зі списку). Якщо запущено з кореня воркспейсу або неясно — показати project map і запитати:

   > "Якого проєкту стосується ця сторі? \<перелік проєктів із project map\>"

3. **Прочитати контекст FE-проєкту:** його `CLAUDE.md` + усі `.claude/rules/*.md` (стек, патерни, конвенції).

4. **Глибокий точковий аналіз коду.** За ключовими словами фічі (з title/description) зробити `Grep`/`Glob`, знайти дотичні файли (компоненти, slices/reducers, api, роути, хелпери) і **прочитати їх цілком** — оцінити що вже реалізовано, чого бракує і яка складність змін.

5. **Бекенд.** З project map визначити бекенд-репозиторій та його шлях. Якщо він доступний — проаналізувати так само (CLAUDE.md/rules + точковий пошук + читання дотичних файлів). Якщо бекенд-репо ще не описане в project map або недоступне за шляхом — оцінити бекенд-частину **лише за описом сторі** і явно це позначити у виводі:

   > "⚠ Бекенд-репозиторій недоступний для аналізу — бекенд-частину оцінено лише за описом."

Висновки цього аналізу (що вже є в коді, що треба додати, складність) використати в Кроці 4 і Кроці 5.

---

## Крок 4 — Естімація

На основі зібраного контексту **та аналізу коду (Крок 3)** зробити оцінку часу виконання сторі (у годинах). Спиратися на те, що вже реалізовано і що доведеться додати/змінити.

Показати оцінку і **обов'язково попередити**:

> "Це моя оцінка з урахуванням наявного коду — перевір її, бо я міг не врахувати всі деталі імплементації."

**Якщо загальна оцінка ≤ 4 годин** — повідомити, що розбивка не потрібна, показати оцінку і **завершити** команду:

> "Орієнтовна оцінка: \<N\> год (≤ 4 год). Розбивка на сабтаски не потрібна."

Якщо оцінка **> 4 годин** — перейти до Кроку 5.

---

## Крок 5 — Генерація сабтасків

Розбити сторі на сабтаски — кожен це **дочірня сторі** з нативними полями Story. Спиратися на аналіз коду (Крок 3): тег `[Frontend]`/`[Backend]` і естімейти обґрунтовувати тим, що вже є в коді й чого бракує.

Правила:
- Кожен сабтаск має оцінку **≤ 4 годин**.
- Поля кожного сабтаска:
  - `name` (title) — з префіксом типу: `[Frontend]` або `[Backend]`
  - `description` — що саме зробити
  - `estimate` — у поінтах (нативне поле Story), **1 поінт = 1 година**
  - `assignee` (owner)
- **Округлення естімейту — завжди ВГОРУ до цілого** (2.5 год → 3 поінти; 1.1 год → 2 поінти).
- **Тип** визначати за контекстом title/description:
  - `[Frontend]` — UI, компоненти, форми, верстка, клієнтська логіка
  - `[Backend]` — API, ендпоінти, БД, серверна логіка, інтеграції
- **Assignee:**
  - `[Frontend]` сабтаски → owner = значення env-змінної `SHORTCUT_MEMBER_ID` (читати через `$env:SHORTCUT_MEMBER_ID` на Windows / `$SHORTCUT_MEMBER_ID` на macOS).
  - `[Backend]` сабтаски → owner не встановлювати.
- Сабтаски мають покривати скоуп сторі без перетину з **уже існуючими** сабтасками (Крок 2).

Якщо є `[Frontend]` сабтаски, але `SHORTCUT_MEMBER_ID` не задано — попередити:

> "`SHORTCUT_MEMBER_ID` не задано (`automation/.env`). Frontend-сабтаски буде створено без assignee. Вказати ID вручну чи продовжити без призначення?"

---

## Крок 6 — Обов'язковий review перед створенням

Показати повний список запропонованих сабтасків:

```
Сторі #<id>: <title> — моя оцінка <N> год

Сабтаск 1: [Frontend] <title>
  Опис: <description>
  Естімейт: <X> поінтів
  Assignee: @<member> (SHORTCUT_MEMBER_ID)

Сабтаск 2: [Backend] <title>
  Опис: <description>
  Естімейт: <Y> поінтів
  Assignee: —
```

Запитати:

> "Створити ці сабтаски? (yes / no / edit N)"

Обробити відповідь:
- `yes` — перейти до Кроку 7 і створити всі сабтаски.
- `no` — скасувати, нічого не створювати.
- `edit N` — показати сабтаск №N детально, дати користувачу внести зміни, потім показати оновлений список і запитати підтвердження знову.

**Без явного `yes` нічого не створювати у Shortcut.**

---

## Крок 7 — Створення сабтасків

Тільки після `yes` — для кожного сабтаска через інструменти Shortcut MCP:
1. Створити **дочірню сторі** з полями `name`, `description`, `estimate`, та `owner_ids` (для Frontend — з `SHORTCUT_MEMBER_ID`).
2. Прив'язати її до батьківської сторі як **sub-task**.

Якщо доступний інструмент MCP не дозволяє прив'язку sub-task або встановлення owner — створити сторі і **зазначити це у підсумку**, щоб користувач доробив вручну.

У підсумку вивести список створених сабтасків з їхніми ID/посиланнями:

```
Створено сабтасків: <count>
- #<id> [Frontend] <title> — <X> поінтів — @<member>
- #<id> [Backend] <title> — <Y> поінтів
<якщо щось потребує ручної дії:>
⚠ Прив'язку sub-task / assignee постав вручну для: <перелік>
```
