# QA Diff

Аналізує зміни у коді та тестує те що було змінено: генерує тест-кейси на основі git diff, запускає Playwright-тести, зберігає звіт зі скріншотами помилок.

**Використання:** `/qa-diff [гілка або "uncommitted"]`

---

## Крок 0 — Збір параметрів

З `$ARGUMENTS` витягнути все що явно вказав користувач. Решту — запитати.

Якщо **проєкт** не вказано і не зрозуміло з поточної директорії:

> "Який проєкт тестуємо?
> 1. THT-myAccount (localhost:3000)
> 2. THT-management (localhost:3030)
> 3. THT-applicant (localhost:3080)
> 4. THT-html-reports"

Якщо **гілка для diff** не вказана:

> "З якою гілкою порівнювати?
> Введи назву гілки (напр. \`main\`) або \`uncommitted\` для незакомічених змін (git diff HEAD)."

Якщо **URL** не вказано — запитати:

> "URL для тестування? (local / stage / prod)
> За замовчуванням для \<project\>: \<default-port-url\>"

Якщо для URL потрібні **credentials** — запитати логін і пароль.

Якщо **формат звіту** не вказано:

> "Формат звіту: MD / HTML / обидва?"

Дочекатися відповідей на всі відсутні параметри перед продовженням.

> Скріншоти робляться лише при помилках тестів — окремо запитувати не потрібно.

---

## Крок 1 — Перевірка змінних середовища

Зчитати значення `QA_TESTCASES_DIR` і `QA_REPORTS_DIR`.

Якщо хоча б одна з них не задана — **зупинитись** і повідомити:

> "Змінна середовища \<назва\> не задана. Будь ласка, налаштуй її перед запуском команди:
> - QA_TESTCASES_DIR — шлях до git-трекованої папки з тест-кейсами
> - QA_REPORTS_DIR — шлях до папки для збереження звітів"

---

## Крок 2 — Отримання git diff

Виконати в директорії проєкту:

- Якщо вказана гілка: `git diff <branch>..HEAD`
- Якщо `uncommitted`: `git diff HEAD`

Якщо diff порожній — повідомити:

> "Змін не знайдено. Перевір чи правильно вказана гілка або чи є незакомічені зміни."

І зупинитись.

---

## Крок 3 — Аналіз diff

Прочитати diff і визначити:
- Які файли змінились
- Яка функціональність зачеплена (нова фіча, виправлення, рефактор)
- Які UI-компоненти або API-ендпоінти можуть бути affected

Сформулювати `<feature-name>` у форматі `lowercase-kebab-case` що відображає суть змін (напр. `user-profile-edit`, `payment-form-validation`).

---

## Крок 4 — Огляд UI через Playwright MCP

Відкрити URL через Playwright MCP і переглянути ті частини інтерфейсу, яких стосуються зміни з diff.

Мета: зрозуміти реальну поточну поведінку до запуску тестів.

---

## Крок 5 — Пошук існуючого тест-кейс файлу

Шлях для пошуку: `$QA_TESTCASES_DIR/<project-name>/`

Переглянути список `.md` файлів. Знайти файл що відповідає зміненій функціональній області (за назвою файлу або заголовком `# Feature Name`).

- Якщо **файл знайдено** — перейти до **Кроку 6б**
- Якщо **файл не знайдено** — перейти до **Кроку 6а**

---

## Крок 6а — Створення нового тест-кейс файлу

На основі diff + спостереженого UI скласти тест-кейси що покривають зміни.

Зберегти файл: `$QA_TESTCASES_DIR/<project-name>/<feature-name>.md`

**Формат тест-кейс файлу:**

```markdown
# <Feature Name>

## TC-001: <Короткий опис>
**Priority:** High / Medium / Low
**URL:** <відносний шлях>

### Steps
1. Крок перший
2. Крок другий
3. ...

### Expected Result
- Що має статися

### Notes
Credentials, залежності, edge cases або —

---

## TC-002: <Короткий опис>
...
```

Продовжити з **Кроком 7**.

---

## Крок 6б — Доповнення існуючого тест-кейс файлу

1. Прочитати файл
2. Визначити останній номер TC
3. Дописати **лише нові** тест-кейси що відповідають змінам з diff — без дублювання існуючих, без їх видалення
4. Продовжити нумерацію від останнього наявного ID

Продовжити з **Кроком 7**.

---

## Крок 7 — Генерація Playwright-коду

На основі тест-кейс файлу (або тільки нових TC якщо файл доповнювався) згенерувати код Playwright-тестів.

**Важливо:**
- Тримати код у пам'яті або тимчасовому файлі
- **Не зберігати** `.spec.ts` файли у директорію проєкту (якщо користувач явно не попросив)
- Для кожного TC — окремий `test()` блок з ID у назві (напр. `test('TC-001: ...')`)
- Якщо потрібні credentials — використати ті що надав користувач

---

## Крок 8 — Запуск тестів через Playwright MCP

Запустити всі згенеровані тести.

При **помилці тесту**:
- Зробити скріншот поточного стану сторінки
- Зберегти у тимчасову папку з іменем `<NN>-tc<id>-<короткий-опис>.png` (де NN — інкрементний номер: 01, 02, ...)

Скріншоти при успішних тестах **не робляться**.

Записувати результат кожного тесту: PASSED / FAILED + деталі помилки якщо є.

---

## Крок 9 — Збереження звіту та скріншотів

Створити папку звіту:
```
$QA_REPORTS_DIR/<project-name>/<feature-name>__<YYYY-MM-DD_HH-mm>/
```

де `<YYYY-MM-DD_HH-mm>` — поточна дата і час запуску тестів.

**Не перезаписувати** існуючі папки — якщо така вже є, додати секунди або суфікс.

Зберегти у цю папку:
- `report.md` — якщо обрано MD або обидва
- `report.html` — якщо обрано HTML або обидва
- Скріншоти помилок з інкрементними префіксами

**Формат report.md:**

```markdown
# QA Report — <Feature Name>
**Date:** YYYY-MM-DD HH:mm
**Project:** <project-name>
**URL tested:** <url>
**Diff:** <branch>..HEAD / uncommitted changes
**Result:** PASSED / FAILED (X/Y tests passed)

---

## TC-001: <назва> — ✅ PASSED / ❌ FAILED

**Steps executed:** (коротко)
**Result:** Що відбулось насправді
**Screenshot:** 01-tc001-short-desc.png (якщо є)

---
```

**Формат report.html** — той самий зміст, обгорнутий у мінімальний HTML з CSS для читабельності.

---

## Крок 10 — Підсумок у чаті

Вивести у чаті Claude Code:

```
QA Diff завершено: <feature-name>
Проєкт: <project-name> | URL: <url>
Diff: <branch>..HEAD / uncommitted changes
Тестів: <total> | ✅ <passed> passed | ❌ <failed> failed

<якщо є провали:>
Провали:
- TC-001: <що пішло не так> → 01-tc001-....png
- TC-003: <що пішло не так> → 02-tc003-....png

Звіт збережено: <повний шлях до папки>
```
